# /restart

呼び出されたら、以下を順に行う。1〜2は読み取り専用の調査のみで、3でユーザーに確認するまでは実装に着手しない。

## 1. 状況を集める

```bash
git status --short
git log -1 --grep='^日記:' --format='%ci %s'
ls -la --time-style=full-iso ~/.claude/plans/*.md
```

- `git status --short`: 未コミットの変更・未追跡ファイルの一覧。これが「実際に何が中断されているか」の一番の手がかりになる。
- `git log`で直近の`/diary`実行時刻を基準点として取得する（`日記.md`はここまでしか記録されていないため、それ以降のplanファイルが「まだ日記に書かれていない、進行中だった可能性が高い作業」になる）。
- `~/.claude/plans/`のplanファイルのうち、mtimeが上記の基準時刻より新しいものだけを対象にする（それ以前のものは既に日記に反映済み、または今回の中断とは無関係と見なして対象外にする）。
- `日記.md`（リポジトリルート）の`# TODO`ブロックと、最新の日付エントリの`### 次にやること`を読む。

## 2. 突き合わせて整理する

- 1で絞り込んだ各planファイルを開き、`git status`に出てきた変更ファイルのbasenameが本文中に登場するかを確認して、「どのplanがどの変更に対応していそうか」を対応付ける（厳密なマッチングでなくてよい、grep的な突き合わせで十分）。
- 対応するplanが見つからない変更ファイルは「plan無しの変更」として別枠にする。
- 内容の無い/意味の分からない未追跡ファイル（0バイトのファイルなど）があれば、実装対象には含めず「正体不明のファイル」として個別に注記するだけにする。
- `flutter analyze`を実行し、現在の未コミット状態がそのままコンパイル可能かを確認する（クラッシュ時に編集途中のまま止まっている可能性があるため）。`~/flutter/bin/flutter`をフルパスで呼ぶ（PATHに無いため）。
- `pgrep -af "flutter.*web-server"`で、起動したままになっている動作確認用プロセスが無いか確認する。見つかった場合は`.claude/skills/server/SKILL.md`の「起動後の扱い」に従い、そのPIDへ`kill -SIGUSR1/2`でホットリロード/リスタートできる旨を案内できるようにしておく（このスキル自身がプロセスを起動・終了させることはしない）。

## 3. ユーザーに提示し、確認する

- 見つかった作業スレッドを、それぞれ「planのタイトル（要約） / 関連する変更ファイル / gitの変更内容の概要」の形で列挙して報告する。
- 「plan無しの変更」があれば、ファイル名と変更内容の概要とともに別枠で報告する。
- `日記.md`のTODOブロックの内容も併せて提示する。
- `flutter analyze`の結果（エラーがあればその内容）を報告する。起動中の`flutter run -d web-server`プロセスが見つかった場合はその旨も伝える。
- 作業スレッドが複数見つかった場合は、`AskUserQuestion`でどれから再開するか確認する。候補が多い場合は関連ファイル数が多い順に上位3件程度＋「まずは全体の状況を把握しただけでよい」を選択肢にする。
- 候補が1件のみ、または「plan無しの変更」しか無い場合は、それを再開してよいか文章で確認してから着手する。
- 中断作業が何も見つからない場合（gitがクリーンで、基準時刻より新しいplanも無い場合）は、その旨と`日記.md`のTODOのみを提示して終える。

## 4. 再開する

- ユーザーが選んだ作業について、対応するplanファイルを読み込み、`git diff`で実際の変更との差分（plan通りどこまで実装済みか、plan外の変更が混ざっていないか）を確認してから続きに着手する。
- 既に一度承認されたplanの続きなので、プランモードには入らず通常の実装作業として進める。
- 確認の結果、plan通り実装が完了しているように見える場合は、その旨を報告し`flutter analyze`・`flutter test`での最終確認と`/diary`の実行を提案する。
- 選ばれなかった他の作業スレッドには手を付けない。
